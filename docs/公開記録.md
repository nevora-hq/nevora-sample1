**このドキュメントは美容室A/B/C専用ではありません。** 飲食店・ネイルサロン・企業サイトなど、

### 実URLと環境変数

`NEXT_PUBLIC_SITE_URL` は**実URLと完全に一致させる**（末尾スラッシュなし）。
この値は canonical・og:url・og:image・robots.txt の Sitemap 行・sitemap.xml の全URLに使われるため、
1文字でも違うと、それらすべてが存在しないURLを指すことになります。

| 記号 | 実URL（本番） | `NEXT_PUBLIC_SITE_URL` |
|---|---|---|
| A | https://hp-template-beauty-a-theta.vercel.app | `https://hp-template-beauty-a-theta.vercel.app` |
| B | https://hp-template-beauty-b.vercel.app | `https://hp-template-beauty-b.vercel.app` |
| C | https://hp-template-beauty-c-sage.vercel.app | `https://hp-template-beauty-c-sage.vercel.app` |

**Vercelが払い出すURLにはサフィックスが付くことがあります**（A は `-theta`、C は `-sage`）。
プロジェクト名から推測せず、デプロイ後に実際に払い出されたURLを必ず確認してください。
※ 上の3つのURLは、canonicalタグの値がそれぞれ自分自身と一致していることを確認済みです。

## 2. 発生したトラブルと対処法（再発防止チェックリスト）

### 2-1. Vercel の Output Directory が `public` のままだと配信されない

**発生：** hp-template-beauty-b

**症状：** デプロイ自体は Ready になるが、サイトにアクセスすると404。

**原因：** Output Directory が `public` に設定されていた。Next.js の静的エクスポートの出力先は
`out/` であり、`public/` は静的アセットの置き場にすぎない。`public/` を配信対象にすると、
ビルド結果のHTMLが1枚も含まれないため全ページが404になる。

**対処：** Vercel の Settings → Build & Development Settings で **Output Directory の Override を外し、
既定のまま**にする。Framework Preset が Next.js なら Vercel が自動で正しい出力先を選ぶ。

- [ ] Output Directory は **Override せず既定のまま**にした（`public` と入力しない）

### 2-2. Framework Preset が `Other` のままだとビルド構成が誤認識される

**発生：** hp-template-beauty-b

**症状：** 2-1と同じく404。ルーティングやビルドコマンドが Next.js 用に構成されない。

**原因：** インポート時の Framework Preset が `Other` のまま作成された。`Other` では Vercel が
Next.js 向けの既定のビルドコマンド・出力先・ルーティングを適用しない。

**対処：** インポート画面で **Framework Preset を `Next.js` に手動で変更**する。
作成後に気づいた場合も Settings から変更して Redeploy すれば直る。

- [ ] インポート画面で Framework Preset が **`Next.js`** になっていることを目視確認した
- [ ] Root Directory は `./`（リポジトリ直下がサイト本体のため）

> **補足：** Vercel CLI（`vercel` コマンド）でデプロイする場合は、ローカルの `next.config.js` から
> Next.js が自動検出されるため、2-1・2-2はそもそも起きません。画面操作でのインポートに
> 不安がある場合はCLIデプロイのほうが確実です（ただしGitHub連携＝push時の自動デプロイは付きません）。

### 2-3. `NEXT_PUBLIC_SITE_URL` が暫定値のまま放置される

**発生：** hp-template-beauty-c

**症状：** サイトは表示されるが、canonical・og:url・og:image・robots.txt の Sitemap 行・
sitemap.xml の6URLがすべて **存在しないホスト**（`https://hp-template-beauty-c.vercel.app`／実URLは
`-sage` 付き）を指していた。

**影響：**
- canonical が404のURLを指すため、**検索エンジンがどのページも正規URLとして登録できない**
- og:image が404になるため、**SNSでシェアしてもOGP画像が表示されない**
- sitemap.xml に載っている全URLがクロール不能

**なぜ起きるか：** `npm run build` の `prebuild`（`scripts/generate-seo-files.js`）は
`NEXT_PUBLIC_SITE_URL` が未設定だとエラーで停止する仕様のため、**初回デプロイ時点では実URLが
まだ分からないのに何らかの値を入れざるを得ない**。この暫定値が、実URL判明後に更新されずに残る。

**対処（初回デプロイは必ず2回に分ける）：**

1. 暫定値を入れて1回目のデプロイ → 実URLが払い出される
2. `NEXT_PUBLIC_SITE_URL` を**実URLに修正**する（末尾スラッシュなし）
3. **Build Cache を使わずに** Redeploy する
   （「Use existing Build Cache」の**チェックを外す**。環境変数はビルド時にHTMLへ埋め込まれるため、
   キャッシュを使うと値が更新されず、修正したつもりで直っていない状態になる）

- [ ] `NEXT_PUBLIC_SITE_URL` が実URLと**完全一致**している（サフィックス・末尾スラッシュ）
- [ ] Redeploy 時に **Build Cache のチェックを外した**
- [ ] Redeploy 後、`curl` 等で canonical・robots.txt・sitemap.xml の値を**実際に確認した**

### 2-4. GitHubリポジトリに自動生成READMEが入っている

**発生：** hp-template-beauty-b、hp-template-beauty-c

**症状：** ローカルで `git init` して作った履歴と、GitHub側の「Initial commit」（自動生成された
`README.md` 1ファイル）が**無関係な履歴**になり、そのままでは push できない。

**危険なのは：** ここで `git push --force` すると、GitHub側のコミットを**確認しないまま破棄**する。
今回はREADME1枚だったので実害はなかったが、他の人が先にpushしていた場合は失われる。

**対処（force push の前に必ず履歴を確認する）：**

```bash
git remote add origin https://github.com/nevora-hq/<リポジトリ名>.git
git fetch origin
git log --oneline origin/main          # ← 何が入っているか必ず見る
git ls-tree -r --name-only origin/main # ← ファイル一覧も見る
```

中身が自動生成READMEだけだと確認できたら、force push ではなく**取り込んでマージ**する：

```bash
git merge origin/main --allow-unrelated-histories
# README.md が add/add で衝突する。こちら側（テンプレートのREADME）を採用する
git checkout --ours README.md
git add README.md
git commit
git push -u origin main
```

C ではこの手順で対応し、force push は使っていません。GitHub側のコミットも履歴に残っています。

- [ ] push前に `git log --oneline origin/main` でリモートの中身を確認した
- [ ] force push を使っていない（使う場合は破棄される内容を把握したうえで）

**リポジトリ作成時の予防策：** GitHubでリポジトリを作るとき、
**「Add a README file」のチェックを外す**（Initialize this repository with のセクション）。
空のリポジトリなら、そもそも履歴の衝突が起きません。

### 2-5. 元画像の幅が足りず、srcSet に書いた幅のファイルが生成されない

**発生：** hp-template-restaurant-a

**症状：** `components/HeroBanner.js` の `srcSet` と `pages/index.js` の preload が
`home-hero-1600.webp` を指しているのに、`optimize-images.py` がその幅を書き出さない。
そのまま公開すると、大画面のブラウザだけが404の画像を取りにいく。

**原因：** 変換スクリプトは**縮小のみ行い引き伸ばしはしない**仕様のため、元画像（1536px幅）より
大きい `-1600` は生成されない。生成ログには「元画像が小さいため -1600 は無効」と出るが、
参照側は自動では直らない。

**対処：** 生成ログの実際の書き出し幅に合わせて、参照側（`srcSet`・preload の `imageSrcSet`・
`WEBP_JOBS`）の3箇所を揃える。飲食店Aでは hero を `640/1024` に統一した。

- [ ] 変換ログに出た幅と、`srcSet`／preload／`WEBP_JOBS` の幅が3箇所とも一致している
- [ ] 出力HTMLが参照する画像パスが**すべて実在**することを機械的に確認した
      （`out/` 内のHTMLから画像URLを抽出し、ファイルの有無を突き合わせる）

### 2-6. 公開前検査で 404ページに h1 が無いことが判明

**発生：** hp-template-restaurant-a

**症状：** 404ページの見出しが装飾の数字「404」（`p.not-found-code`）だけで、`<h1>` が存在しない。
`<title>` は出ているため気づきにくい。

**原因：** 制作基盤テンプレートの404が、数字の表示だけで見出し要素を持たない作りだった。
**この作りは美容室A/B/Cにも残っている可能性が高い。**

**対処：** 数字は `aria-hidden="true"` の装飾として残し、別に `<h1>ページが見つかりません</h1>` を置く。
あわせて数字の色を `--color-primary-light`（地に対して1.81:1）から `--color-text-faint`（5.44:1）へ変更した。

- [ ] 404を含む全ページに `<h1>` がちょうど1つある
