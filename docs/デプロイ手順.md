# デプロイ手順（テンプレートサンプルサイト共通）

制作基盤を複製して作ったテンプレートサンプルサイト（美容室・飲食店ほか各業種のA/B/C）を、GitHubへ登録して
Vercelで公開するまでの手順です。**どのテンプレートでも使い回せるよう汎用的に書いてあります。**
`<...>` の部分は、そのつど自分の値に読み替えてください。

| プレースホルダ | 例（restaurant-a の場合） |
|---|---|
| `<プロジェクトフォルダ>` | `restaurant-a` |
| `<リポジトリ名>` | `hp-template-restaurant-a` |
| `<組織>` | `nevora-hq` |
| `<実URL>` | デプロイ後にVercelが払い出した実際のURL |

実施環境：Windows 11 / PowerShell（`git` と `npm` が使えること）

---

## 手順1. 複製フォルダのGit履歴を作り直す

複製元（制作基盤や他のテンプレート）の `.git` が残っていると、**別リポジトリの履歴とremoteを
引き継いだまま**になります。この状態でpushすると複製元のリポジトリを書き換える事故になるため、
必ず作り直します。

```powershell
cd <プロジェクトフォルダ>

git remote -v          # 複製元のremoteが残っていないか確認
Remove-Item -Recurse -Force .git
git init -b main
```

> 入れ子のフォルダにも `.git` が残っていないか確認してください
> （`Get-ChildItem -Recurse -Directory -Force -Filter .git`）。

## 手順2. 初回コミットを作る

```powershell
git add -A
git ls-files           # 追跡対象を目視確認（下記が含まれていないこと）
git commit -m "<テンプレート名>の初期構成"
```

**コミットしてはいけないもの**（`.gitignore` で除外されているか確認）

- `node_modules/` `.next/` `out/`
- `.env` `.env.local`（`.env.example` `.env.local.example` は追跡してよい）
- クライアント・各種サービスのID/パスワードを書いたファイル

## 手順3. GitHubリポジトリに接続してpushする

```powershell
git remote add origin https://github.com/<組織>/<リポジトリ名>.git
git ls-remote origin   # 接続確認・リモートが空かどうかの確認
```

### リモートが空でない場合

GitHubでリポジトリ作成時に README や .gitignore を追加していると、`Initial commit` が
1つ入っています。どちらかを選びます。

| 状況 | 対応 |
|---|---|
| リモートが自動生成の雛形だけ（履歴を新規に始めたい） | `git push -u --force-with-lease origin main` で上書き |
| リモートに残したい内容がある | `git fetch origin main` → `git merge origin/main --allow-unrelated-histories` → コンフリクト解消 → push |

> `--force-with-lease` は「自分が確認した状態からリモートが変わっていなければ上書きする」オプションです。
> `--force` ではなくこちらを使ってください。上書き前に必ず `git ls-tree -r --name-only origin/main` で
> **消える中身を確認する**こと。

```powershell
git push -u origin main
```

## 手順4. Vercelにインポートする

1. https://vercel.com にGitHubアカウントでログイン → **Add New… → Project**
2. **Import Git Repository** で `<組織>/<リポジトリ名>` を選択
   - 表示されない場合は **Adjust GitHub App Permissions** から対象リポジトリへのアクセスを許可する
   - Private・組織リポジトリではこの許可が必須
3. 設定はすべて既定のままでよい

   | 項目 | 値 |
   |---|---|
   | Framework Preset | Next.js（自動検出） |
   | Root Directory | `./`（リポジトリ直下がNext.jsプロジェクト） |
   | Build Command | `npm run build`（`prebuild` が robots.txt / sitemap.xml を生成する） |
   | Output Directory | 既定のまま |

4. **Environment Variables** に追加する（**必須**）

   | Key | Value | 対象環境 |
   |---|---|---|
   | `NEXT_PUBLIC_SITE_URL` | 暫定値でよい（例：`https://<リポジトリ名>.vercel.app`） | Production / Preview / Development |
   | `NEXT_PUBLIC_GA_MEASUREMENT_ID` | GA4の測定ID | 任意 |
   | `NEXT_PUBLIC_GSC_VERIFICATION` | Search Console の所有権確認 | 任意 |

   `next.config.js` は `NEXT_PUBLIC_SITE_URL` が未設定だと**本番ビルドを意図的に失敗させます**
   （canonical・OGPが黙って欠落するのを防ぐ設計）。設定漏れはビルドエラーで検知されます。

5. **Deploy** をクリックする

## 手順5. 実URLに合わせて環境変数を直し、Redeployする（最重要）

**Vercelは `https://<プロジェクト名>.vercel.app` を割り当てるとは限りません。** 名前が既に使われている
場合、`https://<プロジェクト名>-a1b2c3.vercel.app` のようにランダムな接尾辞が付与されます。

推測値を `NEXT_PUBLIC_SITE_URL` に入れても**ビルドは成功してしまう**ため気づきにくく、
canonical・og:url・sitemap.xml・robots.txt がすべて存在しないドメイン（404）を指した状態で
公開されます。検索エンジンが存在しないURLを正規URLと解釈するため、SEO上の実害があります。

1. デプロイ完了後、**実際に払い出されたURL**を確認する
2. **Settings → Environment Variables** で `NEXT_PUBLIC_SITE_URL` を実URLに更新する
3. **Deployments → 最新のデプロイ → Redeploy** で再ビルドする
   （環境変数を変更しただけでは再ビルドされません）
4. 手順6の確認コマンドで、robots.txt / sitemap.xml / canonical が実URLになっているか検証する

## 手順6. 公開後の確認

`<実URL>` を実際のURLに置き換えて実行します（Git Bash / WSL）。

```bash
B=<実URL>

# 全ページが200を返すか / 存在しないURLが404を返すか
# ページ構成はテンプレートごとに異なるため、scripts/generate-seo-files.js の
# STATIC_PATHS と揃えること
for p in / /price/ /about/ /contact/ /privacy-policy/ /terms/ /sonzai-shinai-url; do
  printf "%-22s %s\n" "$p" "$(curl -s -o /dev/null -w '%{http_code}' "$B$p")"
done

# robots.txt / sitemap.xml のドメインが実URLと一致しているか
curl -s "$B/robots.txt"
curl -s "$B/sitemap.xml" | head -c 400

# canonical / OGP / title が出力されているか
curl -s "$B/" | grep -oE '<link rel="canonical"[^>]*>|<meta property="og:[^"]*" content="[^"]*"|<title>[^<]*</title>'
```

### チェックリスト

- [ ] 全ページが200で表示され、存在しないURLが404を返す
- [ ] `robots.txt` の Sitemap 行が**実URL**になっている（推測値のままでない）
- [ ] `sitemap.xml` の各 `<loc>` が**実URL**になっている
- [ ] canonical / og:url が**実URL**になっている
- [ ] `lib/siteConfig.js` に複製元（NEVORA・他テンプレート）の文言が残っていない
- [ ] 画像（hero / band / logo / favicon / ogp）が用意され、リンク切れになっていない
- [ ] スマートフォン幅で表示が崩れていない
- [ ] お問い合わせフォームが送信でき、実際に受信できる

> **複製元の文言・画像の残存はビルドエラーになりません。必ず目視とgrepで確認してください。**
> `og:site_name` が複製元の屋号のまま公開されるのが典型的な事故です。

### サンプルサイト固有の確認（テンプレートサンプルの場合）

- [ ] 店舗名・住所・電話番号が**架空のもの**になっている（実在店舗の情報を入れない）
- [ ] グローバルナビに本体サイトへのリンクを**置いていない**
- [ ] サンプルであることを示す固定バーが全ページで表示され、リンク先が
      本体サイトの `/contact/?from=<テンプレート記号>` になっている
- [ ] 固定バーの分だけ `body` に余白があり、本文が隠れていない

詳細は `docs/テンプレートサンプルサイト方針.md` を参照。

## 独自ドメインを設定する場合

1. Vercelプロジェクト → **Settings → Domains** でドメインを追加
2. 表示されたDNSレコード（A / CNAME）をドメイン管理会社側に登録する（SSL証明書は自動発行）
3. DNSの反映を待つ（数分〜48時間）
4. `NEXT_PUBLIC_SITE_URL` を本番ドメインに更新し、**Redeploy** する
5. 手順6の確認コマンドを本番ドメインで再実行する

## 以降の更新

`main` へpushすると自動で本番デプロイ、他ブランチへのpushはプレビューデプロイが作られます。

```powershell
git add -A
git commit -m "<変更内容>"
git push
```

## よくある失敗

| 症状 | 原因と対処 |
|---|---|
| `NEXT_PUBLIC_SITE_URL が未設定です` でビルド失敗 | Vercelの環境変数を設定してRedeploy |
| ビルドは成功したが canonical / sitemap が404のURLを指す | 手順5の実URL反映漏れ。環境変数を更新してRedeploy |
| ローカルでは通るのにVercelで失敗 | `package-lock.json` のコミット漏れ、`node_modules` の誤コミットを確認 |
| `pages with getServerSideProps can not be exported` | `output: 'export'` と動的処理の併用。該当ページを静的生成に書き換える |
| pushしたら複製元のリポジトリが書き換わった | 手順1の `.git` 作り直し漏れ。`git remote -v` を必ず確認する |

## コマンドまとめ（2回目以降はここだけ見ればよい）

```powershell
cd <プロジェクトフォルダ>

git remote -v                       # 複製元のremoteが残っていないか確認
Remove-Item -Recurse -Force .git
git init -b main
git add -A
git ls-files                        # 機密ファイル・不要ファイルが無いか確認
git commit -m "<テンプレート名>の初期構成"
git remote add origin https://github.com/<組織>/<リポジトリ名>.git
git ls-remote origin                # リモートが空かどうか確認
git push -u --force-with-lease origin main
```

この後、Vercelでインポート → `NEXT_PUBLIC_SITE_URL` を暫定値で設定 → デプロイ →
**実URLに更新してRedeploy**（手順5）。
